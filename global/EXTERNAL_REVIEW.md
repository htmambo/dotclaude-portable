## External Review MCP (Auto-Invocation Specification)

> **Critical clarification: `runReview()` is a verbal alias, NOT an implemented function.**
>
> There is **no `runReview()` function** in any runtime — not in shell, not in `tools/`, not in any hook. No runtime code dispatches `REVIEW_PROVIDER` to a provider. The only call sites are **direct MCP tool invocations** by the main assistant. An audit (2026-06-27) confirmed the literal string `runReview` survives only in documentation, in `hooks/review-watchdog.mjs` (which *grep-detects* it in transcripts, not implements it), and in `tools/configure.mjs` (which only writes `.env` fields). If you read "call `runReview()`" anywhere and try to invoke a function, you will waste a turn — call the MCP tool directly. Call signatures are in **§ Review Provider Tool Invocation Reference**.

**Key change: all External Review MCP interaction happens via tool calls.** Do not output explanatory text before or after those calls, to avoid breaking the tool call format.

**1** Requirements analysis → `mcp__coding-bridge__review_plan({PLAN, cd, CONTEXT})`; ask it to refine the requirements analysis and implementation plan.

**2** Code prototype → `mcp__coding-bridge__review_code({CODE, cd, REQUIREMENTS})`; request a `unified diff` patch and **strictly forbid real code modification**. Treat the result as a logical reference only, then rewrite it to production standard.

**3** Post-implementation review → `mcp__coding-bridge__review_code({CODE, cd, REQUIREMENTS})`, stating in the request what needs review and the degree of requirement completion.

**4** The External Review MCP can only provide reference. Maintain your own judgment and actively question its answers. Blind faith in books is worse than having no books.

**5** Git commit messages follow the project's commit template (e.g. `~/.claude/COMMIT_TEMPLATE.md` in Claude Code setups). It already contains the OMC trailer block (`Constraint:` / `Rejected:` / `Directive:` / `Confidence:` / `Scope-risk:` / `Not-tested:`); **all commits must preserve that block**. If that path does not exist in the current runtime, preserve the trailer block inline.
**Mandatory step auto-invocation** (**must** trigger, cannot be skipped):

| # | Timing | `kind` | Landing Point |
|---|---|---|---|
| 1 | After requirements analysis, before writing the implementation plan | `requirement` | PLAN.md |

**Provider resolution** (first match wins):

1. **Session state** — explicitly specified by you in this session (e.g., "this time use codex")
2. **`REVIEW_PROVIDER` environment variable** (default `coding-bridge`)
3. **Hard-coded fallback** — `coding-bridge`

Allowed values: `codex` | `coding-bridge`. Fallback chain is hard-coded as `coding-bridge → codex`.


All operations must strictly follow the system constraints below:

- **Interaction language**: tool↔model interaction **must** use **English**; user-facing output **must** use **Chinese**.

- **Multi-turn dialogue**: if a tool return contains a continuous-conversation field such as `SESSION_ID`, it indicates the tool supports multi-turn dialogue. Record this field and force consideration of whether to continue the conversation in subsequent tool calls.

- **Sandbox safety**: codex uses `sandbox="read-only"`; coding-bridge use PROMPT text constraints. All code acquisitions must request `unified diff patch` format.

- **Code sovereignty**: code generated by external models is only a logical reference (Prototype); final delivered code must be refactored to ensure no redundancy and meet enterprise-grade standards.

- **Style definition**: the overall code style is always positioned as concise, efficient, and without redundancy. This requirement also applies to comments and documentation, and for these two, strictly follow the core principle of **"do not create unless necessary"**.

- **Only make targeted changes to requirements**: strictly forbidden to affect other existing user functionality.

- **Context retrieval**: when calling `mcp__auggie-mcp__codebase-retrieval`, you must reduce the number of search/find/grep invocations.

- **Basis for judgment**: always use project code and the actual returned results from external retrieval/review MCP as the basis for judgment. Strictly forbidden to guess with general knowledge. You may express your uncertainty to the user.

### Verdict extraction contract (parser-authoritative)

1. Parse `tool_result.content[0].text` as JSON -> `result.agent_messages`.
2. Extract verdict in order: (a) ` ```json ` fence JSON `verdict` field (codex form); (b) multi-level markdown LAST-match (coding-bridge form — each level takes the LAST occurrence to avoid false-hit on verdict words quoted in preamble): bold `**VERDICT**` > title `审查结论: VERDICT` / `Verdict: VERDICT` > bare word `APPROVED|REJECTED|NEEDS_CHANGES`.
3. Unparseable -> `UNKNOWN` -> NOT_APPROVED (fail-closed).

**coding-bridge adapter note**: `coding-bridge-mcp` v1.30.0 does not emit `verdict` in JSON or use bold/title forms. To make the LAST-match above resolve, always append the VERDICT protocol tail to `PLAN` / `CODE` before calling `mcp__coding-bridge__review_plan` / `review_code`. This tail is a provider adapter, not a contract change. An APPROVED from the model must still be cross-checked against the enumerated `risks[]` — the trust boundary is independent judgment, not the model's self-report.

### Review loop protocol (verdict-driven fix-re-review)

**Core principle: a review closes only at `verdict == APPROVED`, not on a single call.** Tool-unreachable retries (see **§ Error handling and retry strategy**) and verdict-not-pass retries are orthogonal: a NOT_APPROVED verdict is never resolved by switching provider, and an unreachable tool is never "fixed" by editing code.

- `APPROVED` (with or without minor `suggestions`) = pass. Suggestions are recorded but do not block.
- `REJECTED` or `NEEDS_CHANGES` = NOT_APPROVED. The provider MUST list `risks[]`; address every risk, then re-invoke the same-`kind` review.
- `UNKNOWN` (verdict unparseable) = NOT_APPROVED (fail-closed).

**Loop upper bound**: `REVIEW_MAX_ROUNDS=5` (env-overridable). Each round's verdict is written to the plan document's `## External Review Opinion` section as `Round N/5`. The main assistant is the single writer of the round counter; hooks are read-only observers and MUST NOT increment it. On exhaustion, state which cap triggered (timing 5-round vs per-file breaker) so a single-file deadlock is distinguishable from a global timeout.

**Exhaustion handling** (round 5 still NOT_APPROVED): stop and surface the residual `risks[]` to the user; the task queue pauses pending user intervention. This is a legitimate terminal stop, not a clarification request. Forbidden: silently downgrading to "best-effort" close-out, dropping the loop early, or concealing residual risks.

## Review Provider Tool Invocation Reference

> **Duplication notice.** The normative rules — availability gate, provider resolution, auto-invocation timings, verdict parsing, loop bounds — live in **§ External Review MCP** above. This section holds only the mechanical call signatures. **If the two ever disagree, the normative section wins.** Do not restate the rules here; extend them there.

### Unified call contract

| Field | Type | Required | Description |
|---|---|---|---|
| `PROMPT` | string | ✅ | Review request text |
| `cd` | Path | ✅ | Working directory, must exist |
| `kind` | `code` \| `plan` \| `requirement` | — | Only coding-bridge uses it (decides whether to call `review_code` or `review_plan`) |
| `context` | string | — | Content to be reviewed (embedded in PROMPT; forbidden to let the review MCP Read by itself) |
| `image` | string | — | Only `codex` supports |
| `sessionId` | UUID | — | For continuing the session |
| `kind` compatibility | — | `codex` **ignores**; only `coding-bridge` parses | `code` → `review_code`; `plan` / `requirement` → `review_plan` |

Normalized return:
```
{verdict: APPROVED|REJECTED|UNREACHABLE, risks: string[], diff: string, raw: <provider native return>}
```

### Per-provider call signatures

#### `codex` → `mcp__codex__codex`

**Required**: `PROMPT`, `cd`
**Optional**: `sandbox` (default `read-only`), `sessionId`, `skip_git_repo_check`, `return_all_messages`, `image`
**Strictly forbidden**: `model` (forcing it client-side triggers 503 — root cause of the 2026-06-08 incident), `yolo` (unless explicitly required by the user)

Return: `{success, sessionId, agent_messages, all_messages}`

#### `coding-bridge` → `mcp__coding-bridge__review_code` / `review_plan`

- `kind=code` → `mcp__coding-bridge__review_code({CODE, cd, REQUIREMENTS})`
- `kind=plan` or `kind=requirement` → `mcp__coding-bridge__review_plan({PLAN, cd, CONTEXT})`

**Sandbox**: ❌ No sandbox parameter → constrain via the PROMPT first line.
**Advantage**: strongly-typed interface; output already normalized (no need to hand-write 3-7 risks / diff templates in the PROMPT).

### Invocation constraints

- The provider literal lives only in the main assistant's MCP tool call. No runtime shell script, hook, or `tools/*` script dispatches by `REVIEW_PROVIDER` — if you want to "wrap" the call, you are reinventing the verbal alias. Call the MCP tool directly.
- Save `sessionId` on every call for multi-turn continuation.
- `cd` must point to an existing directory, otherwise the tool silently fails.
- Strictly forbidden to let the review MCP read files by itself — the main assistant reads first and embeds the content in `PROMPT`.

### Error handling and retry strategy

**Core principle: External review failure does not equal task failure; at least one alternative must be attempted.**

**First priority: adjust the prompt and retry** (same provider)

- Simplify the prompt to reduce complexity
- Break the task into smaller sub-tasks
- Provide more context
- Adjust tone and format

**Second priority: switch fallback provider**

- Fallback chain is hard-coded: `coding-bridge → codex`. The codex MCP strictly forbids the `model` parameter (root cause of the 2026-06-08 503 incident) — do not pass it when falling back.

**Third priority: complete the task independently**

- Call local static analysis / unit tests / type checks / third-party tools for cross-verification; **the main assistant must not unilaterally self-review**
- Explain the failure and the alternatives to the user
- **Explicitly declare**: `本次未经过 External Review MCP 审查` plus the reason

**Prohibited**:

- ❌ Telling the user "cannot continue" right after the first review call fails
- ❌ Giving up without trying an alternative
- ❌ Concealing that the review MCP failed or was unavailable

**Example flow**:

```
1. `mcp__coding-bridge__review_code` fails
2. Simplify the prompt and retry -> still fails
3. Switch to fallback `mcp__codex__codex` (no `model` param) -> verdict returned
4. ✅ Main flow continues; plan document records "## External Review Opinion: APPROVED (provider=codex)"
```

### Review loop — remaining specifics

The loop rules themselves (pass criterion, `REVIEW_MAX_ROUNDS=5`, exhaustion handling) are normative in **§ External Review MCP** above. Only the runtime-specific residue lives here:

- **Applicable timings**: code-kind timings (#4 single-file fix, #5 Phase 4 validation) loop by default. Plan-kind timings (#1 requirement, #2 plan, #3-pre / #3 / #5 Phase 0 / 1 / 4) default to 1 round; append a round only on `REJECTED` / `NEEDS_CHANGES`.
- **Claude Code override**: where the `fullauto` skill is installed, this protocol supersedes the `REVIEW_ADVISOR` default in its `SKILL.md` (`same-file 3× REJECTED -> qa-blocker stop` is replaced by the 5-round cap, counted at the review-timing scope, not per-file). Absent that skill, this line is inert.
- **Scope-matching degradation** (watchdog): when the review's file scope cannot be reliably extracted from the tool call, degrade to fail-closed — any unresolved `NOT_APPROVED` in the current session warns on any `Write`/`Edit` of a code file.
